# AI 同事功能增强设计方案

**日期**：2026-06-07  
**状态**：待实现

---

## 背景

现有 AI 同事功能存在以下核心问题：

- 不 @ 任何人时消息无人接收，路由依赖用户手动
- 每次对话都是全新上下文，AI 没有记忆
- 消息发出后无任何处理中的反馈
- 频道消息多后话题混乱，无法追溯对话链条

本设计方案解决上述问题，并重新定义同事状态的产品语义。

---

## 一、频道管理员

### 定位

每个频道自动拥有一个**不可删除**的管理员角色，作为频道的默认接线员。未 @ 任何人时，消息由管理员接收、分析、路由。

### 交互流程

```
用户发消息（不 @任何人）
  → 管理员接收，分析消息意图
  → 管理员在频道中公开回复，@对应同事：
    "这个登录 Bug 需要前端排查，@全栈工程师 帮忙看一下？"
  → 对应同事接收任务，在频道中继续回复
```

### 配置项

| 字段 | 说明 |
|------|------|
| 昵称 | 默认"频道管理员"，可修改 |
| 系统提示词 | 决定路由策略和语气，每个频道独立配置 |
| 模型 | 始终继承全局默认，不可单独设置 |

### UI 展示

- 管理员显示在同事列表**顶部**，带特殊标识（皇冠图标）
- 与普通 AI 同事视觉区分，但交互一致

## 二、上下文记忆

### 三层记忆结构

```
层 1 — 频道整体摘要（所有同事共享）
  历史消息的压缩，提供宏观背景，批量更新

层 2 — 话题快照（每个话题独立）
  当前活跃话题的进展摘要，定时更新（非实时）

层 3 — 同事个人笔记（每位同事独立）
  该同事在此频道积累的关键信息，体现个性
```

**频道隔离**：不同频道的记忆完全独立，互不影响。

### Prompt Cache 优化排列

为最大化 prompt cache 命中率，上下文按稳定性从高到低排列：

```
[Cache 断点 1 — 深度缓存，极少变化]
  系统提示词
  同事个人笔记
  频道整体摘要

[Cache 断点 2 — 定时快照，周期性变化]
  其他活跃话题摘要（非实时，每 N 条消息更新一次快照）

[不缓存 — 每条消息都变]
  当前话题完整消息
```

> **设计原则**：其他话题使用快照而非实时摘要，避免其他话题的每条新消息都破坏缓存前缀。

### AI 回复时的上下文组装

```
同事 X 回复话题 T 时：
  系统提示词
  + X 的个人笔记
  + 频道整体摘要（历史背景）
  + 其他活跃话题摘要快照（X 未参与的，只给摘要感知）
  + 话题 T 的完整消息（X 正在参与的，给全文）
```

首次被 @进入某话题的同事，自动获得该话题树的完整历史作为引入上下文。

### 存储结构（SQLite 新增表）

```sql
-- 频道整体摘要
channel_memories (
  channel_id TEXT PRIMARY KEY,
  summary    TEXT,
  updated_at TEXT
)

-- 话题树摘要快照
topic_summaries (
  topic_id      TEXT PRIMARY KEY,  -- 对应根消息的 id
  channel_id    TEXT,
  summary       TEXT,
  message_count INTEGER,           -- 快照时的消息数，用于判断是否需要更新
  updated_at    TEXT
)

-- 同事个人笔记
colleague_notes (
  colleague_id TEXT,
  channel_id   TEXT,
  notes        TEXT,
  updated_at   TEXT,
  PRIMARY KEY (colleague_id, channel_id)
)

-- 记忆更新队列（防止 app 关闭时丢失更新）
memory_jobs (
  id         TEXT PRIMARY KEY,
  type       TEXT,    -- 'channel_summary' | 'topic_snapshot' | 'colleague_notes'
  payload    TEXT,    -- JSON，包含 channel_id / topic_id / colleague_id
  status     TEXT DEFAULT 'pending',   -- 'pending' | 'done'
  created_at TEXT
)
```

### 记忆更新机制

| 记忆类型 | 触发时机 | 更新内容 |
|---------|---------|---------|
| 频道整体摘要 | 话题关闭时（超过 X 分钟无新消息） | 将该话题压缩后追加进频道摘要 |
| 话题快照 | 话题每新增 N 条消息（建议 10 条） | 重新生成当前话题摘要，覆盖旧快照 |
| 同事个人笔记 | 每次 AI 回复后 | AI 自判断"这次对话有什么值得长期记忆"，有则追加 |

**可靠性保障（防 app 意外关闭）**：

```
AI 回复完成
  → 同步写一条 memory_jobs 记录到 SQLite（不阻塞）
  → 异步处理该 job
  → 处理完成标记 done

app 启动时
  → 检查 memory_jobs 里的 pending 记录
  → 补跑未完成的更新任务
```

> 原始消息始终同步落库，摘要是派生物，即使丢失一次更新，下次启动可自动补算。

## 三、正在输入状态

- AI 开始处理时，频道消息流中显示该同事的"正在输入..."动画（三点闪烁）
- 通过 IPC 事件驱动：主进程发送 `ai:typing-start` / `ai:typing-stop`，渲染进程响应显示/隐藏
- 同一时间多个同事处理中时，分别独立显示各自的输入状态

---

## 四、同事状态重定义

### 语义调整

状态不再表示"空闲/忙碌"（这对 AI 没有意义），改为表示**当前任务承载**：

| 状态 | 含义 | UI 展示 |
|------|------|---------|
| 可接任务 | 当前没有正在处理的任务 | 绿色点 · 空闲 |
| 处理中 | 正在执行 1 个或多个任务 | 黄色点 · 处理中 |

- 同事列表和频道消息中的头像旁均显示状态点
- @ 一个"处理中"的同事时，输入框给出轻提示："全栈工程师正在处理其他任务，消息已排队"

## 五、引用回复（替代 Thread）

### 设计依据

产品场景是"用户 + AI 同事"的协作空间，没有多人类用户需要整理讨论的问题。Slack Thread 的核心价值（避免干扰他人）在此场景不成立。引用回复更轻量，无需导航进出，保留聊天感。

### 交互

- 悬停任意消息 → 出现"回复"按钮
- 点击后输入框顶部显示被引用消息的摘要卡片
- 发出的消息上方带引用卡片，点击可跳转回原消息
- AI 回复 @提及消息时，自动引用被 @的消息

### 多条回复的视觉展示（树状缩进）

```
用户
  @全栈工程师 登录页有 bug
│
├─ 全栈工程师
│    我来看看，能描述报错吗？
│
├─ 管理员
│    @运维专家 也确认下部署配置
│   │
│   └─ 运维专家
│        我查一下日志...
│
└─ 全栈工程师
     找到了，是 token 过期问题
```

- 同一消息的多条回复以兄弟节点并列展示
- 层级关系通过视线引导线（竖线）连接，层级上限建议 3 层，避免过深嵌套
