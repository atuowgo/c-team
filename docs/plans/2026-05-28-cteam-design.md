# c-team 产品设计文档

> 日期：2026-05-28
> 状态：设计完成，待实现

## 概述

c-team 是一个 **Electron 桌面应用**，面向个人开发者（单人 + N 个 AI 同事），提供 AI 原生的项目协作空间。核心理念：AI 不是工具，而是拥有独立角色身份的"同事"，在频道、看板、代码仓库中与人类平等协作。

**一句话描述**：让你一个人 + 若干个 AI 同事，像一个完整团队一样工作。

## 第二部分：数据模型

### 工作空间结构

每个项目 = 一个独立工作空间：

```
my-project/
├── .cteam/                   ← 工作空间数据目录
│   ├── workspace.db          ← SQLite（频道、看板、工单、AI 同事配置）
│   ├── ai-profiles.json      ← AI 同事角色定义
│   └── settings.json         ← 项目级配置
├── src/                      ← 你的实际代码
└── ...
```

### SQLite 核心表

| 表名 | 用途 |
|------|------|
| `channels` | 频道列表（名称、类型） |
| `messages` | 消息历史（频道、发送者、内容、时间、AI上下文引用） |
| `boards` | 看板列表 |
| `columns` | 看板列（名称、顺序） |
| `tickets` | 工单（标题、描述、状态列、assignee、优先级、关联PR） |
| `ai_colleagues` | AI 同事（名称、角色、提示词、能力集、当前状态） |
| `ai_task_queue` | AI 待处理事件队列 |
| `integrations` | 外部集成配置（GitHub token 等） |

## 第三部分：AI 同事体系

### 角色档案（Profile）

每个 AI 同事由以下构成：
- 名称、头像、角色描述（如 "Ada · 后端工程师 · 擅长 Python/Go"）
- 系统提示词（System Prompt）：定义行为风格、专业边界
- 工作范围（Scope）：限定订阅哪些频道、能操作哪些看板/仓库
- MVP 预设 2-3 个角色（工程师、运维、通用助手），后续支持自定义

### 状态机

```
空闲 → 任务监听中（接收新消息/工单分配）
     → 工作中（生成计划/写代码/审PR）
     → 等待反馈（需要人类确认或补充信息）
     → 空闲
```

关键规则：
- 每个 AI 同事**单线程执行**，同一时间只处理一个任务
- 允许最多 N 个 AI 并行工作（N 用户可配置，默认 2）
- 状态对用户完全透明——UI 右侧栏实时可见

### 行为能力

| 能力 | 说明 |
|------|------|
| 聊天 | 在频道中收发消息、回复 @提及、主动汇报 |
| 看板操作 | 创建/认领/移动工单、写评论、改标签 |
| 编码 | 读取仓库、建分支、写代码、提交 PR、响应 review |
| 巡检（二期） | 定期检查 PR 状态、过期工单等，主动告警 |

## 第四部分：AI 调度引擎

### 事件驱动模型

调度引擎是 Electron 主进程中的常驻服务，监听三类事件：

| 事件来源 | 示例 |
|---------|------|
| 用户操作 | 发送消息、分配工单、批准方案、合并 PR |
| 外部回调 | GitHub webhook（PR 新 review、CI 结果） |
| AI 内部 | 一个 AI 完成任务，触发下一个排队任务 |

### 调度流程

```
事件入队 → 匹配 AI 同事（角色/范围是否覆盖该事件）
         → 检查状态（空闲 / 工作中 / 等待反馈）
         → 空闲 → 立即分配执行
         → 工作中 → 比较优先级，决定排队还是打断
         → 等待反馈 → 事件排队，不打断
```

### 优先级规则

1. 用户 @AI → **最高优先级**，打断当前任务
2. 工单状态变更（如 PR review 意见到达）→ **高优先级**，可打断
3. 用户分配新工单 → **普通优先级**，排队
4. 定时巡检 → **最低优先级**，仅空闲时执行

### AI 执行循环

```
接收任务 → 加载上下文（频道历史、工单描述、关联代码）
         → 调用 Claude API（角色 system prompt + 工具定义）
         → 解析响应（消息 / API 调用 / 混合）
         → 执行动作（发消息、操作工单、调 GitHub API）
         → 汇报结果 → 状态回空闲 → 取下一个排队任务
```

## 第五部分：频道系统

### 频道类型

| 类型 | 说明 |
|------|------|
| 项目频道 | 围绕一个项目/仓库，可绑定 GitHub repo 和项目看板 |
| 话题频道 | 自由主题 |
| AI 广播频道 | 系统级，AI 进度汇报、巡检告警自动推送 |

### 消息模型

- **普通消息**：文本、代码块
- **AI 消息增强**：内嵌可操作卡片（如 "Ada 提交了 PR #42 → [查看 diff] [批准] [要求修改]"）
- **系统消息**：看板状态变更、CI/CD 结果通知
- 消息支持线程回复

### AI 在频道中的行为

- 被 @ 时立即响应（打断当前任务，最高优先级）
- 完成任务后在关联频道主动汇报
- 检测到需要人类决策时暂停并等待
- AI 之间可以在频道中公开对话，全程透明

### 设计原则

- AI 发言始终有明确归属，不可匿名
- AI 不能修改或删除他人消息
- 所有 AI 消息保留上下文链接，便于溯源

## 第六部分：共享任务看板

### 看板结构

- 每个看板绑定一个项目/频道
- 默认四列：**Todo → In Progress → In Review → Done**，可自定义增减
- 工单字段：标题 + 描述（Markdown）+ 标签 + 优先级 + Assignee + 截止日期 + 关联 PR

### AI 与看板的交互

- 人类将工单拖到 Todo 并设置 AI 为 Assignee → AI 空闲时自动认领
- AI 开始工作前在评论区写执行计划
- 编码类工单完成后关联 PR，移至 In Review，频道汇报
- 非编码类工单完成后产出贴到评论，移至 Done
- AI 判断工单描述不清晰 → 移回 Todo 并 @创建者请求补充

### 与 GitHub 的关系（第一期）

- 看板工单可以**关联** GitHub Issue，但不强制 1:1 映射
- AI 创建 PR 后，PR 状态反向显示在看板工单上

### 视图

- 标准 Kanban 视图（主力）
- 按 Assignee 分组视图（查看每个 AI 的负载）
- 按优先级排序列表

## 第七部分：编程会话

### 完整生命周期

```
工单分配 → AI 制定方案 → 人类确认 → AI 编码 → 提 PR → 人类 Review → 合并 → 完成
```

### 方案阶段

- AI 认领工单后，先在评论区提交执行方案（改动范围、技术方案、预估量）
- 人类批准或要求修改
- 简单工单可跳过方案阶段直接编码

### 编码阶段

- AI 通过 GitHub API 创建功能分支
- 逐个文件写入/修改代码
- 每次提交附带清晰 commit message
- 进度实时可见（"已完成 3/5 个文件"）
- 编码中发现问题时暂停并 @人类求助

### PR 阶段

- AI 创建 PR，填写描述，关联工单
- 工单自动移至 In Review，频道通知
- 人类提 review 意见后，AI 自动读取并修改
- PR 合并后工单自动 Done，AI 频道汇报

### 异常处理

| 场景 | 策略 |
|------|------|
| PR 冲突 | AI 尝试自动解决，失败则 @人类 |
| CI 失败 | AI 读取日志尝试修复，最多 3 次循环 |
| 工单范围膨胀 | AI 提议拆分为多个工单 |

## 第十部分：技术栈选型

| 层 | 选型 | 理由 |
|----|------|------|
| Electron 脚手架 | **electron-vite** | Vite 驱动，HMR 极快 |
| 前端框架 | **React + TypeScript** | Chat/Kanban 组件库最丰富 |
| UI 样式 | **Tailwind CSS + shadcn/ui** | 设计质量高，暗色模式内置 |
| 状态管理 | **Zustand** | 极轻量，API 简洁 |
| 本地数据库 | **better-sqlite3** | 同步 API，Electron 事实标准 |
| AI SDK | **@anthropic-ai/sdk** | 官方 SDK，支持 streaming/tool use/caching |
| GitHub | **Octokit (@octokit/rest)** | GitHub 官方 JS SDK |
| 打包分发 | **electron-builder** | 跨平台打包 |

**架构原则**：AI 编排自己写轻量层，不引入 LangChain 等重型框架——调度逻辑是核心差异化。

## 第十一部分：MVP 范围

### 必做

**AI 同事基础**
- 预设 2-3 个角色（工程师、运维、通用助手）
- 独立 system prompt + 能力集
- 状态机 + 右侧栏状态面板

**频道系统**
- 创建/删除频道
- 文本消息收发（Markdown）
- @AI 同事触发对话
- 消息持久化到 SQLite

**看板系统**
- 创建看板 + 自定义列
- 创建/编辑/拖拽工单
- 分配 AI 为 Assignee
- 工单评论（Markdown）

**编程会话（核心闭环）**
- AI 认领工单 → 方案 → 确认 → 编码 → PR → Review → 合并

**GitHub 集成**
- OAuth 认证
- repo 绑定
- 基础 API：读文件、建分支、写文件、提交、PR、读 review

**基础设置**
- Claude API key 配置
- GitHub token（OAuth）
- AI 并发数设置
- 暗色/亮色主题

### 二期

| 推迟项 | 原因 |
|-------|------|
| Slack/Discord adapter | 先专注本身体验 |
| Linear/Jira adapter | 二期 |
| AI 定时巡检 | 先做好按需响应 |
| 用户自定义 AI 角色 | 先用预设 |
| 多窗口/系统托盘 | 二期 |
| 自动更新 | 发布前再加 |

### MVP 验收标准

用户能完成完整流程：
1. 打开 c-team，创建项目工作空间，连接 GitHub repo，配置 Claude API key
2. 在频道里与预设 AI 同事对话
3. 在看板上创建编码工单并分配给 AI
4. AI 提交执行方案，用户批准
5. AI 建分支、写代码、提 PR
6. 用户在 GitHub review，AI 自动修改
7. PR 合并，工单 Done，AI 频道汇报
